Firefox MCP Extension Research and Design Notes

Research summary and proposed design for a Firefox extension that can start and stop a local MCP server, expose browser tab metadata, and grant controlled read, interaction, scripting, and screenshot access to individual tabs.

Executive Summary

The proposed system is feasible with a Firefox WebExtension plus a Native Messaging host. Most of the browser-control primitives already exist. The novel engineering work is primarily the authorization model: per-tab grants, read-only versus read-write access, temporary versus persistent access, capability-specific grants, and composable access-control rules.

The recommended architecture is to keep the Firefox extension as the final authorization boundary. The native MCP server should never be trusted merely because it is local. Every sensitive request should be revalidated by the extension against the current grant set.

Recommended Architecture

   +-- Tab metadata access
   +-- Read-only page proxy
   +-- Structured interaction API
   +-- Optional scripting capability
   +-- Screenshot capability
   +-- Audit and revocation UI

Clicking the toolbar icon can call runtime.connectNative(), which launches a registered native application. Disconnecting the native port can terminate the host. This maps well to an explicit start/stop server UX.

The native process should bind only to 127.0.0.1 or ::1, authenticate MCP clients, and validate HTTP origins where appropriate.

Capability Model

Rather than model permissions as only RO and RW, use orthogonal capabilities internally: 

READ
INTERACT
SCRIPT
SCREENSHOT

RO and RW then become presets: 

RO = READ
RW = READ + INTERACT

SCRIPT should remain separate because arbitrary JavaScript effectively bypasses most of the practical distinction between observation and interaction. SCREENSHOT should also remain independent because visual capture can reveal information that is absent from serialized DOM data.

Suggested Grant Shape

Grant {
    client_id
    tab_id
    document_id
    rule_id
    capabilities
    lifetime
    created_at
}

Suggested lifetimes:

  • ONCE — one operation or one request chain.
  • DOCUMENT — valid until navigation replaces the document.
  • TAB_SESSION — valid until the tab closes.
  • PERSISTENT_RULE — determined by the ACL engine.

Read-Only Proxy Design

A Greasemonkey-like isolated execution environment is not sufficient to guarantee read-only access. Isolated code can still perform mutations and initiate actions.

The recommended design is to expose only serialized page data and never return live DOM handles, references, callable objects, or arbitrary evaluators. 

PageView {
    document_id
    url
    title

    query(selector)
    text(selector?)
    links()
    forms()
    attributes(selector)
    computed_style(selector)
    accessibility_snapshot()
}

Every result should cross the content-script boundary as data. The MCP server should have no direct object that can later be used to invoke page-side behavior.

Permission Request UX

Firefox cannot expose a new browser-owned permission type for the extension's custom RO/RW semantics. The extension therefore needs an extension-owned prompt. 

MCP requests page access
        |
        v
Extension checks active grants
        |
        +-- granted -> execute
        |
        +-- not granted
                |
                v
        toolbar badge / popup request

"This client wants access to:
 GitHub - PR #123

 Access:
 ( ) Read only
 ( ) Read + interact

 [ ] Allow screenshots
 [ ] Allow scripts

 Duration:
 ( ) Once
 ( ) Until document changes
 ( ) Until tab closes
 ( ) Always for matching rule

 [Decline] [Allow]"

The prompt should identify the MCP client or session, not just the requested tab. This becomes important once more than one local client can connect.

Access-Control Language

The ACL engine should be separate from Firefox's own host-permission system. Firefox permissions determine whether the extension is technically allowed to operate. The ACL determines whether a particular MCP capability is authorized.

Example

allow(
    host("localhost")
    OR host("*.internal.example.com")
    OR (
        regex("^https://github\.com/[^/]+/[^/]+/pull/\d+")
        AND NOT glob("*/settings/*")
    )
)
-> [read, interact]

allow(
    glob("https://docs.example.com/**")
)
-> [read, screenshot]

Parse these rules into an explicit AST instead of evaluating user-provided expressions: 

Or
 +-- Host(localhost)
 +-- And
     +-- Regex(...)
     +-- Not(Glob(...))

URL normalization should be specified carefully. Important decisions include:

  • Scheme handling.
  • Case folding of hostnames.
  • Punycode and internationalized domains.
  • Default-port normalization.
  • Path percent-decoding behavior.
  • Whether query strings are included in matching.
  • Whether fragments participate in matching.
  • How redirects affect an existing grant.

For regular expressions, a RE2-compatible engine is preferable to unrestricted backtracking JavaScript regexes if practical, because pathological regular expressions should not be able to lock the extension event page.

Localhost Policy

"Localhost enabled by default" should be defined explicitly. A practical default set is: 

localhost
*.localhost
127.0.0.0/8
::1

Default access should preferably be READ only. Localhost frequently hosts database consoles, development dashboards, cloud emulators, admin interfaces, OAuth callbacks, and services containing credentials.

Screenshot Design

Screenshots should be a separate grant from DOM read access. A screenshot can reveal canvas contents, images, remote desktop sessions, visually rendered secrets, and other information not available through a sanitized DOM proxy.

For background-tab screenshots, Firefox requires broad <all_urls> authority for tabs.captureTab(tabId). This means Firefox may see the extension as broadly capable even though the extension promises the user a narrow per-tab policy.

Recommended approach:

  • Keep background screenshot support optional.
  • Request the broad browser permission only when the user enables this feature.
  • Always recheck the internal capability grant before capture.
  • Audit every capture event.

The native host and its registration manifest must be installed separately from the Firefox extension package.

Security Boundary

The extension should be the final policy enforcement point. The native MCP server should never send an already-authorized command such as "execute this because policy said yes." Instead, it should send the requested operation and context, and the extension should perform the final check. 

MCP request
    |
    v
native host
    |
    v
extension receives exact requested operation
    |
    +-- validate client/session
    +-- validate tab/document identity
    +-- evaluate ACL
    +-- evaluate temporary grants
    +-- validate capability
    +-- write audit entry
    |
    v
execute or deny

This protects against bugs or compromise in the localhost MCP process and avoids treating "local" as equivalent to "trusted."

Arbitrary Scripting

Arbitrary scripting is technically possible, but it should be designed as a separate high-risk capability and considered independently from structured interaction.

A safer v1 can expose extension-owned structured operations:

  • Click.
  • Focus.
  • Type.
  • Set form values.
  • Submit.
  • Scroll.
  • Navigate.
  • Read DOM-derived structured data.

This keeps authorization understandable and makes audit logging useful. Arbitrary JavaScript can be added later after the Firefox distribution and policy implications are settled.

Recommended MVP

  1. Firefox extension with toolbar start/stop state.
  2. Native Messaging host that runs a local MCP Streamable HTTP endpoint.
  3. Read-only tab metadata exposed without page access.
  4. Per-tab request flow for READ and INTERACT.
  5. Temporary grants tied to document and tab lifetime.
  6. Persistent ACL rules using host, glob, and regex predicates.
  7. Boolean AND/OR/NOT composition.
  8. Serialized read-only page facade.
  9. Structured click/type/scroll/navigation operations.
  10. Separate SCREENSHOT grant.
  11. Audit log and immediate revocation.
  12. Defer arbitrary SCRIPT capability until the rest of the security model is stable.

Key Design Principle

An MCP client may discover that a tab exists, but crossing from metadata into page content, page interaction, scripting, or screenshot access requires an explicit, revocable capability granted by the user or by a user-defined policy rule.

This capability-broker model is the main differentiator from existing Firefox MCP tools, which tend to be either intentionally read-oriented or broadly privileged automation systems.
